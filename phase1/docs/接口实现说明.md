# 接口实现说明（技术 → 产品）

> 对应 `docs/接口数据字段说明.md` v1。回答三个必须先确认的问题，并列出实现与文档的差异。
> 代码位置：`cxcy/phase1/`（单人 MVP，未推送）

## 一、结论：三个字段能不能产出

| 字段 | 能否产出 | 由谁产出 | 说明 |
|---|---|---|---|
| `open_hours` / `closed_days` | ✅ 能 | **后端知识库**，不是 Dify | 32 条 POI 全部带 `open_hours`；`closed_days` 由“周一闭馆”解析成 `[1]`；没有的返回 `null`，前端显示「待核实」 |
| `transport.from_prev_min` | ✅ 能（估算） | **后端按坐标算** | 两点直线距离 × 经验速度：≤1.2km 步行、≤6km 公交、更远打车；首项为 0。**不是高德路径规划**，误差 ±30% |
| `weather` | ⚠️ 能，但是示例值 | 后端按月份气候表 | `source` 如实标 `model`；接和风天气后改 `weather_api`，字段结构不变 |

**结论：P2 的时间校验和 P4 的贴士密度不依赖 Dify 产出这些字段**，Dify 只负责“需求解析 + 路线候选”的语义部分，
确定性字段（营业时间、耗时、天气、预算）全部由后端保证。

→ **不需要按文档第八节整体降级**。只有单个 POI 缺 `open_hours` 时，那一条标「待核实」并跳过时间校验，
其余照常，`status` 变 `partial`。

## 二、字段怎么来的（便于对齐）

| 字段 | 来源 |
|---|---|
| `item_id` | 数据库主键，形如 `it_17`，**增删后不漂移**（详见差异 1） |
| `start_time` / `end_time` | 排程时按“最早可进入时间 + 时长 + 30 分钟通勤”顺推，`end = start + duration` |
| `cost` / `cost_breakdown` | 按类型归集：景点→ticket、餐饮→food、住宿→hotel、交通→transport，四项之和等于 `cost` |
| `source` | 知识库条目为 `knowledge_base`；模型补的点（暂时没有）会标 `model`，用户手改为 `user` |
| `warnings` | 时间重叠、闭馆、营业时间、排队久、雨天路滑 |
| `budget.categories[].over` | 只和参考占比（20/20/35/25%）比，仅用于标黄，**不参与超支判定** |
| `tips.weather_tips` | 逐日天气 + 雨/高温 → 生成 actions（带伞、防晒、防滑鞋） |
| `meta.agents` | 五个智能体各自的耗时，页面可做生成过程可视化 |

## 三、实现与文档的差异（需要产品确认）

1. **`item_id` 用 `it_{数据库id}`，不是 `it_001`**
   文档里 `it_001` 是示例。按顺序编号会在删除/重排后指向错位，所以用主键，保证“全局唯一、编辑时按它定位”。

2. **`request.destination` / `people` / `start_date` 由后端补**
   请求只传 `raw_text`、`day_count`、`budget_limit`；目的地从文本解析（识别不到默认长沙），
   人数从文本解析（默认 1），出发日默认“下一个周六”。

3. **天气是示例气候，`source=model`**
   没有接真实 API。前端按文档渲染即可；接 API 后只改后端一处，字段不变。

4. **地图：不做内嵌地图，改为跳转高德**
   每条后面有「地图」按钮，跳 `https://uri.amap.com/marker?position=lng,lat&name=...&callnative=1`，
   手机上会直接唤起高德 App 并定位到该点。**不引入地图 SDK**，避免 Key、坐标系、移动端兼容三个坑。
   如果需要“把当天点位按顺序连成路线”，高德 URI 支持 `path`，但要先做路径规划，属于第二阶段。

5. **结伴相关接口未实现**
   按“本阶段收窄到单人 MVP”的决定，删除结伴页面与 `members` 表，接口只有单人链路。

6. **`days[].items` 允许为空数组**（那天没排到地方），此时 `status=partial`，前端渲染空态而不是报错。

## 四、联调 checklist 自测结果

`scripts/check_spec.py` 按文档第九节逐条断言，全部通过：

```
✓ days 长度等于 day_count          ✓ items 是数组而非 null
✓ cost 等于 cost_breakdown 之和     ✓ budget.total 等于四类之和
✓ categories 固定四类且顺序正确      ✓ remaining = limit - total
✓ limit 为 null 时 over_budget 恒 false
✓ PATCH 回完整且自洽的 budget        ✓ 删除后该条不在 days 里
✓ 保存接口返回 saved                ✓ 已保存列表非空
✓ 错误码 INSUFFICIENT_INFO / NOT_FOUND，message 为中文
```

## 七、v1.1 新增字段（前端已在用，文档待补）

按设计稿还原界面时加了两个字段，都属于"只增不改"，不影响现有解析：

| 字段 | 类型 | 说明 |
|---|---|---|
| items[].labels | string[] | 界面标签：免费 / 需预约 / 人多 / 住宿，前端渲染成小胶囊 |
| meta.adjustments | object[] | 自动调整记录：{day_index, to_day, item_id, name, message}，行程页顶部显示"已自动调整" |

### 自动调整规则（校验智能体的落地）

1. 非最后一天 → **顺延到次日末尾**，时间接在当天最后一条之后 +30 分钟；
2. 最后一天 → **换成同区域、当天开放的同类地点**（例：岳麓书院周一闭馆 → 换成橘子洲）；
3. 换不到 → 移除，并在 meta.adjustments 里如实写原因。

判定依据：closed_days 命中当天星期，或 start_time 不在 open_hours 区间内。
"需预约"目前只是标签（POI 的 
eed_booking 字段），不做预约接口。

### 界面与设计稿的对齐情况

- 底部 tab：规划 / 行程 / 我的（行程页内嵌预算条，预算与贴士仍为独立页）
- 行程页顶部：预算条（预算 · 已用 · 人均 · 剩余 + 进度）
- 条目卡：时间轴、交通耗时、标签、点击看详情
- 预算页：四色堆叠条（门票蓝 / 交通青 / 餐饮橙 / 住宿紫），分类占比偏高标黄

## 八、v1.2 新增：模型接入与一句话改行程

### 模型分工（方案 C）

| 环节 | 谁做 |
|---|---|
| 需求解析（meta.parse_source = "llm"） | DeepSeek |
| 排程 / 校验 / 预算 | 代码（可复现） |
| 贴士文案（	ips.note，
ote_source = "model"） | DeepSeek，只润色给定事实 |
| 一句话改行程 | 模型输出动作 JSON，代码执行 |

没配 LLM_API_KEY 时全链路走规则，meta.model 为 local-rules。

### 新接口

| 接口 | 用途 |
|---|---|
| POST /api/trips/{trip_id}/command | {text:"把第二天下午删掉"} → 完整行程 + command:{ok,action,message} |
| POST /api/chat | 新增 known 字段（前端已填的天数/预算），支持“缺什么问什么” |

### 新增字段（只增不改）

| 字段 | 说明 |
|---|---|
| meta.model | deepseek-chat 或 local-rules |
| meta.parse_source | llm 或 local |
| 	ips.note / 	ips.note_source | 模型润色的一段提示语；失败时为 null |
| command | 仅 command 接口返回 |

> 模型只在“理解语言”和“写文案”两处出现，排程与金额永远由代码计算，避免幻觉。

### 错误码补充（v1.3）

| 错误码 | 场景 | 返回内容 |
|---|---|---|
| BUDGET_TOO_LOW | 预算低于最低可行线（TC-04） | message + minimum + suggestions + llow_force |
| UNKNOWN_CITY | 地名不认识（TC-05） | message + supported |
| NO_DATA | 城市认识但没收录 | message + supported |

最低成本估算：住宿 130×（天数-1） + 餐饮 45×2×天数 + 杂项 40×天数。
用户坚持要用低预算时，请求加 "force": true 即可强行生成（行程会标 over_budget）。
